# Browser-local learner save contract

`schemaVersion` is independent of bundled content's `formatVersion` and `contentVersion`. The save is one JSON object, not a serialized practice session. Decoding and migration are pure in-memory operations; they do not read or write storage. Callers supply a new `snapshotId` on version-0 migration (or use the codec's generated identity); a later explicit save must compare against the original stored raw text before replacing it. A failed migration leaves that text untouched.

## Version 1 (current)

The envelope has `schemaVersion: 1`, `savedAtEpochMs`, `snapshotId`, `revision`, `preferences`, `lessonProgress`, `practiceProgress`, `reviewItems`, and optional `personalGlossary`. Encoding emits every field, including default and null fields. Preferences contain `colorMode` (`system`/`light`/`dark`), `showReadings`, `showTranslation`, and `showRomaji`. Lesson records contain `lessonId`, `contentVersion`, `updatedAtEpochMs`, `stage` (`situation`, `dialogue`, `understanding`, `guidedPractice`, `rolePlay`, `summary`), nullable `checkpointId`, and nullable `completedAtEpochMs`. Review records contain `itemId`, `documentId`, `outcome` (`again`/`hard`/`good`), `lastReviewedAtEpochMs`, nullable `dueAtEpochMs`, `intervalMs`, `step`, `repetitions`, `lapses`, and `lastActionToken`.

Practice records contain one latest checkpoint per `setId`: `contentVersion`, `updatedAtEpochMs`, `runToken`, `lastTransitionToken`, ordered `exerciseIds`, matching ordered `exerciseTypes` (`choice`/`reading`/`completion`/`production`), ordered compact `outcomes`, `frontier`, `view`, and nullable `lastCompletedAtEpochMs`. Types allow restoration to reject IDs reused for a different exercise kind, even for unresolved prompts; a missing or mismatched type list is invalid. Learning records contain no saved answer, response text, authored content, or history. Explicitly saved personal glossary notes are a separate collection. See `SaveModels.kt` and `SaveValidation.kt` for exact wire names, enumerations, defaults, bounds, and frontier consistency rules. Unknown but syntactically valid content IDs are retained without catalog lookup.

## F07 lesson place and recovery

A lesson record is a checkpoint, not a serialized lesson session. Situation and Summary use a null item checkpoint; null also means entry to any other stage, including an empty Dialogue/Understanding/Guided Practice stage or objective-only Role-play. Non-null IDs must match an executable item **in the saved stage**: dialogue turns in Dialogue, choice exercises in Understanding, reading or completion exercises in Guided Practice, and production exercises in Role-play. Conversation-graph nodes are not F07 items. The catalog and player resolve through the same lesson plan. A different `contentVersion` alone does not invalidate stable stage/item IDs. Saved completion is independent of whether the current checkpoint is available.

Looking up a checkpoint and ordinary Resume are read-only: Resume opens that stage/item without moving the record or restoring prior responses or feedback. The version-1 lesson record contains no answers or feedback; an exercise resumes at its prompt with a notice that previous responses and feedback were not restored. Opening a preview or catalog status likewise makes no write. A missing lesson document is unavailable, **not** a reason to synthesize a replacement lesson or erase its saved record. If the document exists but an ID was removed, moved to another stage, or denotes an unsupported graph node, show an incompatible saved place and offer Back to Topics or explicit Continue from Situation. Keep the original record until the learner chooses recovery; recovery writes a Situation/null checkpoint through the save owner, preserving existing completion and all review records. Do not silently repair on load, status projection, or Resume. Stage-entry null checkpoints remain valid regardless of whether a stage has items.

`visitLesson` records ordinary stage/item transitions (including entering Summary) and preserves prior completion; it does not complete a lesson. Explicit Finish calls `completeLesson` through the save owner with the encountered lesson ID, current validated content version, and completion time. This is **one** validated mutation of that lesson record: it sets Summary with a null checkpoint and completion together, even if the saved place was older. It keeps the first `completedAtEpochMs` on replay, and a repeated Finish at the same Summary/version is unchanged (no additional write or refreshed timestamp). After a revisit moves the place, Finish can restore Summary without erasing that first completion. Invalid values or an unencountered lesson are rejected with the prior snapshot intact. Neither mutation changes review scheduling, other lesson/practice records, or envelope write metadata; the owner supplies write metadata on an accepted change. Completion denotes finishing the sequence, not mastery. No response, feedback, or current-session outcome is serialized.

## Version 0 (compatibility fixture)

Version 0 is a **new compatibility/test fixture introduced with F03**, not a learner-save format previously shipped by this repository. Its object must contain exactly the top-level fields `schemaVersion: 0`, `savedAtEpochMs`, `preferences`, `lessonProgress`, and `reviewItems`; no version-1-only fields are accepted. Its `preferences` must contain `colorMode`; the three study-support booleans may be absent and then default to `showReadings: true`, `showTranslation: true`, `showRomaji: false`. Present booleans are preserved. Lesson and review records use the version-1 wire shapes: the nullable lesson checkpoint/completion and review scheduling fields may be absent (default null); all other record fields are required. Arrays themselves and the preferences object are required, even when empty. No additional fields are accepted at any level.

Migration first validates the precursor's wire types, records, timestamps, IDs and limits, then supplies only those documented absent defaults. It preserves existing records and timestamps, creates empty `practiceProgress` and `personalGlossary` collections, sets `revision` to zero, injects a new bounded `snapshotId`, and validates and byte-checks the resulting version-1 envelope. It returns `migratedFrom: 0`; re-encoding the migrated snapshot produces version 1. Invalid input, an invalid generated identity, or a throwing identity supplier returns `Protected(INVALID_SNAPSHOT)` rather than partially migrating; the original raw text remains available for recovery.

Missing, malformed, negative, fractional, or unsupported versions (including future versions) are protected, never guessed as version 0 or downgraded. Duplicate keys, unknown fields, bad types/enums, impossible records, oversized input, and excessive JSON depth are also protected. Protected text is not truncated, rewritten, or exposed as a usable save by the codec.

## Portable backup (format 1)

`BackupCodec.encodeBackup(snapshot, appVersion, exportedAtEpochMs)` wraps the complete validated version-1 save in a JSON object with exactly these fields:

```text
backupFormatVersion: 1
appId: "hiragame"
appVersion: string
exportedAtEpochMs: integer
save: complete SaveEnvelope object (not an abbreviated snapshot)
```

`backupFormatVersion` is separate from `save.schemaVersion` and bundled content versions. `appVersion` is informational (1–64 ASCII characters from `[A-Za-z0-9._+-]`), not a compatibility gate. In the site export path, its authority is Gradle's generated `SiteBuildInfo.VERSION` from `site/build.gradle.kts`, not imported metadata. `exportedAtEpochMs` is the UTC export time, distinct from the save's `savedAtEpochMs` write time; both use integer milliseconds in `0..253402300799999`. Export reads the current validated owner memory, including accepted changes not confirmed saved, without changing learner metadata or storage. `ProgressDownloads` requests a `hiragame-backup-YYYY-MM-DD.json` download with `application/json;charset=utf-8`; a requested download does not prove the file was retained.

`BackupCodec.decodeBackup(raw, newSnapshotId)` accepts format-1 wrappers containing supported schema-1 or schema-0 saves, bare schema-1 saves, and bare schema-0 compatibility fixtures. A bare save has no source app version or export time; only its snapshot date is available. Schema 0 is the F03 compatibility fixture described above, not a previously shipped learner format. It migrates in memory before preview and never writes on decode. Wrapper markers commit to wrapper validation: an invalid wrapper, wrong `appId`, or unsupported version cannot fall back to a bare save. Invalid JSON, duplicate keys (including escaped equivalents), unknown fields, unsafe IDs, unsupported save versions, and invalid types/records are rejected with fixed categories, not parser text or imported content.

Limits apply **independently**: the entire backup is at most `2 MiB + 4 KiB` UTF-8 JSON and 34 nesting levels; the original nested `save` JSON (or entire bare save) must itself be at most `2 MiB` and 32 levels, counting whitespace and escapes, not just normalized serialization. Migration revalidates and byte-checks the resulting version-1 save. The save additionally caps IDs/tokens at 128 characters (`[A-Za-z0-9][A-Za-z0-9_-]*`), revision at `9007199254740991`, combined lesson/practice records at 1,000, review records at 5,000, and exercises per checkpoint at ten; see `SaveValidation.kt` for remaining bounds. Unknown but syntactically valid content IDs survive without a catalog check. Import validation does not promise those records are playable or calculate review availability.

A restore round trip preserves learner payload (preferences, personal glossary entries, lesson/practice/review records, including their timestamps and checkpoint tokens), not the imported envelope's write metadata: on successful local replacement, the owner assigns a fresh local `snapshotId` and `savedAtEpochMs` and advances its local revision once. For a protected original, a successful explicit replacement starts revision at zero. The import's identity/revision are never overwrite authority. Export alone changes none of these values.

## Replacement and reset ownership

The site `LocalProgressOwner` alone authorizes `beginRestore(ValidatedBackup)` or `beginReset(ResetScope)` and consumes a one-use token with `confirmReplacement`; preview/selection do not authorize a write. Confirmation validates and encodes before storage access, rereads the acknowledged raw baseline, and makes one guarded write before publishing and invalidating old practice sessions. Restore **replaces, not merges**, all local learner progress, personal glossary entries and preferences. `PROGRESS_ONLY` clears lessons, practice checkpoints, and review items (including unknown-content records) but keeps every current preference and personal glossary entry. `FULL_LEARNER_STATE` clears those collections and the personal glossary and uses `SavePreferences()` defaults (system color mode, readings/translation on, romaji off). Either successful reset stores a valid new snapshot under `hiragame:state`, not a removed key; unrelated keys, legacy color-mode text, and offline assets/caches are not cleared. Failed or canceled replacement does not activate the candidate or discard the prior save or active practice.

An unreadable/unsupported stored original is kept untouched for separate exact-text `.txt` recovery when it can be read. This text is **unvalidated**, not an importable validated backup. Explicit warned restore or full reset can replace it against the exact protected baseline; progress-only reset is blocked because its preferences cannot be recovered. An unknown baseline (failed startup read) or conflict blocks replacement until safe reconciliation; a newly discovered existing value requires explicit reload before review. The owner compares raw text on reread and the store compares again immediately before writing, but comparison plus write is **not atomic cross-tab compare-and-swap**: simultaneous tabs can still race. No automatic merge or retry of failed replacement occurs.

Backups are manual, browser/device/origin-local portability: export a JSON file and manually transfer/select it to restore elsewhere. Browser storage clearing can erase the local save. There is no account sync, cloud upload, or automatic backup; learner reset does not delete offline content.

## O04 personal glossary

The optional `personalGlossary` field extends the initial schema-1 release with a default empty list; earlier schema-1 saves lacking it continue to decode with identical learning data and no synthetic notes. Encoding includes the field. Older development builds that do not recognize the field protect it as unknown data instead of dropping it; use this or a newer build to open these backups. Schema 0 migration starts with an empty glossary.

At most 100 entries are accepted. Each has a unique stable `id`, required nonblank `term` (up to 256 characters), optional `reading` (up to 256) and required nonblank `meaning`/example (up to 500). Term/reading reject control characters; meaning permits newline/tab only. These strings are rendered as literal personal text, never HTML or approved curriculum. Entry edits/removals compare the prior entry, and UI actions also check the save owner generation. Backups preserve entries; preview counts them; progress reset retains them and full reset explicitly clears them. Unsaved glossary drafts are transient and defer offline activation while being edited.
