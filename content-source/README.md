# Content authoring

This directory holds source material, unreviewed migration drafts, and review evidence—not a runtime loader or learner saves. The canonical, reviewed JSON tree is `site/src/jsMain/resources/public/content/`: `catalog.json` lists grouped hiragana, katakana and introductory vocabulary micro-sets alongside the original romaji beginner set and six bundled workplace lessons: five complete starter lessons and the preserved short meeting-time seed. Topics offers read-only previews, not an interactive lesson player. Every new practice document contains 1–10 exercises so its entire authored plan is reachable in a bounded session. Format-1 contracts live in `shared/src/commonMain/kotlin/com/github/nanaki_93/content/` (`ContentModels.kt`, `ExerciseGraph.kt`); `ContentCodec.kt` strictly decodes individual documents. The read-only `tools/validate_content.py` checks the complete canonical tree and review evidence. Neither decoding nor validation promotes drafts automatically. Home and Topics load same-origin bundled JSON; canonical-source validation alone does not prove production packaging, browser behavior or deployment.

## Preserved legacy source and topic routing

`legacy/question.csv` is a byte-for-byte preservation copy of `backend/migration/question.csv`. Do not edit either file during conversion. See `review-notes/legacy-inventory.md` for the source SHA-256, parser-derived record/mode and topic-label counts, every observed label, aliases, and known uncertainty. The headerless CSV has ten fields: ID, Japanese, romanization, translation, topic, level, mode, timestamp, katakana flag, kanji flag. Parse with Python `csv.reader` and `newline=""`; commas and quotes may occur within fields.

`topic-map.json` has `formatVersion: 1` and an exact-match `labels` object: **each raw CSV topic label → one stable routing topic ID**. Require an explicit mapping for any new label; never silently slug/fold an unknown label. Multiple raw labels may point to the same ID only when deliberately declared as aliases. Check alias collisions by grouping labels by ID: the current shared-ID groups differ only in casing (`casefold()` equality); any future semantic merge must be inspected and documented rather than produced by automatic normalization. Do not change an existing ID merely because display text changes. The raw `N5` topic on `SIGN` rows maps specifically to provisional `kana-signs`, **not** to a level-based curriculum topic. The level column remains distinct and does not select a topic.

This map is draft routing, not reviewed content or a rights decision. `legacy-*` IDs and the `kana-signs` ID do not automatically create canonical catalog topics; promotion requires independent content and rights review. No legacy romanization, reading, translation, or character flags have been approved by this preservation step. Conversion is described below; see `review-notes/legacy-inventory.md` for the complete SIGN/kana audit, including omissions, duplicates, historical signs, and suspect or context-sensitive readings.

## Identity and versions

Wire names are explicitly annotated with `@SerialName`; JSON keys use camelCase. `formatVersion` is required and currently exactly `1`; `contentVersion` is a required positive integer (currently `3` in the canonical tree). Catalog and documents must share both versions; the canonical validator checks this. These are **content** versions, separate from learner save `schemaVersion: 1`. Stable seed and practice IDs are unchanged across the content-version bump; compatible practice checkpoints can still resume on Home. Topics reports lesson checkpoint availability without actually resuming a lesson (F07). Difficulty is advisory, never a proficiency certification or unlock rule.

Stable IDs match `[A-Za-z0-9][A-Za-z0-9_-]*` (ASCII only; existing hyphenated UUIDs fit). Do not derive IDs from a title, translation, list position, or hash. Keep IDs on reordering, copy corrections, or a `contentVersion` increase; give a materially new learning objective a new ID. Catalog topic IDs are unique among topics, document IDs among entries, and audio IDs among assets. Phrase, exercise, and review-item IDs each have their own **catalog-wide** namespace across all documents. Speaker, dialogue-turn, grammar-note, and graph-node IDs are local to their owning document; choice-option IDs are local to their owning **exercise** (the same option ID may occur in a different exercise). Local checks live in the models where available; the canonical validator resolves cross-document and local references and enforces catalog-wide uniqueness. IDs in references retain their owning context: catalog entries identify the document, and `targetKind` plus `targetId` identifies the local review target. Referenced lesson prerequisites are lesson IDs, not display labels.

Required properties have no default empty-string values. Lessons must explicitly include `phrases` and `reviewItems` arrays (empty is allowed); practice sets may omit those two arrays, which then default to empty. Explicit `null` is not an empty array. Other lists and audio references may be omitted only where declared optional. Catalog entries specify `kind` (`lesson` or `practice`), `topicId`, and a relative `path`; the validator enforces path safety and existence. A dialogue declares speakers and ordered turns; turns refer to speaker IDs. Phrases can link to a source turn and optionally to a catalog audio ID. No recording is required for text-only content. `JapaneseText` requires a surface, authored reading, and **exactly one** translation or isolated-kana sound/usage gloss. A gloss is reserved for a single precomposed hiragana or katakana sign (not a kana-only word, contracted pair, or standalone length mark); use a translation for those other surfaces. Its optional segments must concatenate exactly to the surface; any segment containing kanji/iteration marks, including supplementary-plane CJK ideographs, needs an authored reading. Non-kanji punctuation or mixed code segments can omit a segment reading. No pronunciation or answer variants are inferred from romanization. Register and context notes are optional; phrases also require usage and register. Role-play criteria are self-assessment prompts, not grading rules. Review metadata records reviewer type, date, review-note reference, provenance, rights status and basis; merely constructing metadata does not constitute rights clearance. The validator requires reviewed status, publishable rights, and affirmative evidence scoped to each bundled document.

## Exercises and conversation graphs (format version 1)

Both lessons and practice sets have an `exercises` list. Each exercise has a required `id` and a `type` discriminator: `choice`, `reading`, `completion`, or `production`. A choice has a prompt, at least two stable-ID options, one `correctOptionId`, and an explanation. An option has exactly one of `label` (e.g. an English meaning) or authored Japanese `text`. A reading has an authored `stimulus` (normally Japanese; the basic-sign typed-kana sets use an explicit Latin syllable cue to elicit the kana spelling), an explicit `answerRepresentation` (`kana` or `romaji`), nonempty `acceptedAnswers`, and an explanation. Each accepted answer also has a `type` matching that representation: `kana` carries `text: JapaneseText` (surface, authored reading, and translation or isolated-kana gloss); `romaji` carries a nonblank literal `text` string. Mixed representations and duplicate readings after boundary trim and Unicode NFC (kana surfaces or romaji strings) are rejected by both Kotlin decoding and the Python validator; this is not transliteration or script conversion. A completion has a template with exactly one literal `{blank}`, nonempty authored Japanese `acceptedAnswers`, an authored `expectedCompletedExample`, and an explanation. A production has a communication prompt, authored Japanese `exampleResponses`, and self-assessment `criteria`—**no** exact-match answer or correct-option field. Accepted variants must be explicitly authored. Choice grading matches the option ID exactly; kana and romaji reading comparison trims boundary whitespace then applies NFC to submitted and authored answers (so decomposed dakuten/handakuten can match). It does **not** fold case, width, script, macrons, long vowels, small kana, punctuation or internal spaces. Constrained completion trims boundary whitespace only and compares the exact fill surface (no NFC or punctuation/code-like folding); free production is learner self-assessed against examples and criteria, not exact-string or paraphrase graded. No unlisted pronunciation or romanization equivalent is inferred. The romaji visibility preference only shows authored aids, never changes an exercise's answer representation. Japanese examples, completion fills, and kana reading answers use `JapaneseText`; only romaji answer spellings are plain strings.

A lesson may have a `conversationGraph` with an `entryNodeId` and typed `nodes`: `prompt` (declared `speakerId`, authored `text`, `nextNodeId`), `choiceInteraction` (choice `exerciseId`, option-ID `transitions` each with contextual `feedback` and `nextNodeId`), `completionInteraction` (completion `exerciseId`, `feedback`, `nextNodeId`), and `terminal` (message, no outgoing edge). The lesson owns its graph, referenced speakers, exercises, options, and node IDs; no cross-document edges are implied. Graph node IDs are unique within their lesson; choice-option IDs within each choice exercise; exercise IDs across the catalog. In version 1 the graph must be reachable from its entry, acyclic, have transitions for every choice option, and lead to a terminal; repeat an interaction by authoring new nodes, not a back edge. The canonical validator checks these properties and dangling edges. These types describe content, not runtime conversation behavior.

## Convert to unreviewed drafts

From the repository root:

```sh
python3 tools/convert_legacy_content.py --input content-source/legacy/question.csv --topic-map content-source/topic-map.json --output content-source/drafts/legacy
python3 -m unittest discover -s tools -p 'test_convert_legacy_content.py'
cmp backend/migration/question.csv content-source/legacy/question.csv
```

The checked-in `drafts/legacy/drafts.json` contains 4,946 records in CSV order. Each record keeps the exact parsed ten source field strings, including its unchanged UUID, plus a 1-based source record/line location and explicit mapped draft-routing topic. The top-level SHA-256 binds it to the preservation copy. `draftFormatVersion` is **not** the canonical content `formatVersion`. Every record has `reviewStatus: unreviewed`, `authoredReading: null`, and unresolved reading, meaning/translation, classification (including mode, topic, level and flags), and provenance/redistribution findings. Legacy romanization is retained only as a source claim; it is **not** an inferred kana reading. The draft is not a lesson, exercise, review decision, or publishable-rights declaration; it stays outside `site` resources.

The converter parses the headerless CSV with Python `csv.reader` (including quoted commas/newlines), validates every record and the explicit map before writing, and reports row/UUID diagnostics for malformed columns, invalid or repeated UUIDs, flags, unsupported modes and unmapped labels. It rejects colliding map aliases, output in the source CSV directory or application resources, and any existing output differing in bytes **or** containing extra files. An identical rerun leaves the existing file untouched; failures do not overwrite it. To incorporate source changes, review the difference and explicitly move the old output aside before regenerating—never discard reviewed notes as an automatic side effect. No rights are inferred from the repository license. The complete SIGN inventory audit is in `review-notes/legacy-inventory.md`.

## Review and explicit promotion

Do not copy a draft, legacy row, or F00 mock into the canonical tree on the strength of its presence here. For each proposed item, review the meaning, authored reading, translation/gloss, naturalness and register, accepted variants, classification, provenance, and redistribution/publication rights. Resolve uncertainty before inclusion; retain source UUIDs where reused. Independently author or revise a format-1 lesson or practice document, add a catalog entry under `site/src/jsMain/resources/public/content/`, and write a review note under `content-source/review-notes/` before explicitly promoting it. `review.reviewNote` is a relative path beneath that notes directory; set `status: reviewed` and `rights: publishable` only for actually reviewed and cleared content.

Follow `review-notes/f01-seed.md` for the existing evidence convention, `review-notes/f05-foundations.md` for the dated F05 practice decisions, and `review-notes/f06-starter-lessons.md` for the five F06 lessons' dated, document- and nested-ID-scoped language/rights decisions. Before adding or revising a lesson, check its meaning, naturalness, authored readings/ruby and translations, register, variants, distractors, communication intent, provenance and rights; resolve or omit uncertain material, then record the specific decisions under its document ID. Evidence requires a dated `Reviewed on ... by ... Scope: ...` decision naming the document ID, matching its metadata reviewer type and date, documented provenance and an affirmative publishable rights basis. Cover **every** nested ID (exercises, options, phrases, review items, speakers, turns, grammar notes, graph nodes) with item-specific meaning/reading/variant decisions, via scoped inherited review and an ID-covered decision table or explicit reviewed-item decisions. An unrelated ID mention or inherited metadata alone is not coverage. Distinguish AI-agent review from human review; do not claim native-speaker certification or third-party permissions not obtained. The repository license does not clear external source text, recordings, or legacy rows. The existing seed note records original agent-authored text, not a blanket approval of converted material. Contradictory, pending, or restricted decisions must be resolved before publication; the validator checks evidence structure, not the truth of linguistic or legal claims.

## Validate canonical content

From the repository root, after explicit promotion (or to verify the current reviewed catalog):

```sh
python3 tools/validate_content.py site/src/jsMain/resources/public/content --review-root content-source/review-notes
```

A successful check verifies structure, versions, IDs and references, graphs, review evidence, normalized reading-variant uniqueness and local assets; it does not package assets, load them in the app, certify linguistic correctness, or grant rights. The validator rejects unlisted JSON, CSV/drafts in the canonical tree, unsafe paths and symlinks. `tools/test_f05_content.py` asserts practice coverage; `tools/test_f06_content.py` asserts the five IDs/objectives, order, six-lesson bundle, required material and version/seed preservation. These structural checks do not substitute for the item-level agent review in `review-notes/f06-starter-lessons.md`. Complete canonical coverage and packaging must be verified at the F06 final gate, not by this guide. No audio, historical kana, exhaustive loanword combinations, pitch accent or comprehensive phonetics are shipped as part of F05. `ContentCodec` handles strict single-document decoding; the CLI handles cross-document checks.

## Optional audio in format 1

Text-only content needs no audio. To add a recording, declare it in `catalog.json` `audioAssets` with a stable `id`, a local relative `path` under `audio/` (inside the canonical content root), an exact `transcript` matching the linked dialogue turn or phrase's Japanese `text.surface`, and a `permissionNote` explicitly granting publication of **the recording**. Link the asset ID via that turn or phrase's `audioId`, place the file at the declared path, and include a recording-specific reviewed decision and publication permission for the backticked audio ID in that document's scoped review note. Text/transcript rights do not grant rights to a recording. Do not introduce remote or traversal paths or assume that validation establishes deployed audio availability.

## Authoring helpers (O03)

`python3 tools/author_content.py new --id lesson-my-topic --topic-id workplace-clarification --title "My topic"` creates an unreviewed draft with stable IDs, a dialogue, four exercise templates, phrase/review references and a graph. Add `--kind topic` or `--kind audio` for those scaffolds. It refuses to overwrite an existing draft and never calls a model.

`python3 tools/author_content.py validate-draft content-source/drafts/lesson-my-topic.lesson.json` checks structure only. It does not approve language or rights. Replace all TODOs, author/review readings and meanings, and document original provenance or actual redistribution permission in `review-notes/`. Complete explicit per-item agent/human review and the draft's metadata before promotion; do not imply human review.

`python3 tools/author_content.py promote content-source/drafts/lesson-my-topic.lesson.json` is the explicit publication-to-repository step. Optional `--topic-draft` adds a new topic. It first validates the existing tree, stages the entire next content version, validates all schema/reference/review/audio requirements, then writes the verified files with the catalog last. Ordinary write failures restore prior files; abrupt process/system termination is not a multi-file transaction, and the content validator detects partial versions. It never deploys a site, rewrites stable existing IDs or adds authoring dependencies to the application bundle. Drafts remain outside production. No AI-generated material is promoted automatically.
